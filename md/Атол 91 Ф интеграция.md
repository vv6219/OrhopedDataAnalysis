# Архитектурный план: Интеграция ККТ «АТОЛ 91Ф» в ОртоERP (54-ФЗ / ФФД 1.05 и 1.2)

## 1. Анализ исходного плана и критические уточнения

Исходный план верно выделяет ключевые аппаратные ограничения кассового аппарата **АТОЛ 91Ф** (ньюджера в режиме фискального регистратора):
1. **Монопольный доступ к COM-порту**: физический виртуальный COM-порт и библиотека `fptr10.dll` не допускают параллельных вызовов из нескольких потоков;
2. **Медленный тракт печати (57 мм)**: время фискализации и печати может достигать 10–25 секунд;
3. **Критерий истинности фискализации (Popper Test)**: факт обрыва или замятия бумаги не отменяет запись чека в Фискальный Накопитель (ФН). Решающим является флаг `LIBFPTR_PARAM_DOCUMENT_CLOSED`, а не `LIBFPTR_PARAM_DOCUMENT_PRINTED`.

### Выявленные архитектурные пробелы, требующие доработки:
- **Разрыв между Node.js/Express и C# .NET**: в проекте основной бэкенд написан на Express.js (Node.js, порт 5000), а клиент — на React 19. Необходим четкий контракт взаимодействия: автономный легковесный .NET 8/9 сервис-демон (Kestrel REST API на порту 5050) либо прямой проксируемый мост с гарантированной очередью.
- **Отсутствие схемы аудита в БД**: необходимо физическое создание таблиц `fiscal_receipts` и `fiscal_audit_logs` в единой базе SQLite (`db/orthopedic_data_center.sqlite`) для синхронной записи структурированных логов Serilog и истории всех фискальных операций.
- **Автономный режим эмуляции (Mock Mode)**: для стендов разработки, тестирования и работы при отключенном кабеле ККТ кассовый сервис обязан иметь прозрачный режим эмулятора (`AtolMockDriver`), возвращающий реалистичные номера ФД и ФПД без сбоев.
- **UX интеграции в Оформление визита**: в пошаговом мастере (`CheckoutWizard.tsx`) опция фискализации должна быть органичной: свитч/чекбокс, автоподстановка телефона/email пациента для тега 1008 ФФД, индикатор статуса кассы и отображение ФД/ФПД на финальном экране.

## 3. Модель данных в SQLite (Таблицы аудита и чеков)

В базе данных `db/orthopedic_data_center.sqlite` создаются две специализированные таблицы:

### 3.1. Таблица фискальных чеков `fiscal_receipts`
```sql
CREATE TABLE IF NOT EXISTS fiscal_receipts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  transaction_id INTEGER REFERENCES operation_transactions(id) ON DELETE SET NULL,
  visit_id INTEGER REFERENCES patient_visits(id) ON DELETE SET NULL,
  patient_id INTEGER REFERENCES patients(id) ON DELETE SET NULL,
  patient_contact TEXT,                    -- Тег 1008 (Телефон / Email)
  receipt_type TEXT NOT NULL DEFAULT 'sell', -- 'sell' (приход), 'sell_return' (возврат)
  payment_type TEXT NOT NULL,              -- 'card', 'cash', 'sbp', 'invoice'
  total_amount REAL NOT NULL,              -- Сумма чека (₽)
  tax_type INTEGER DEFAULT 6,              -- LIBFPTR_TAX_NO (Без НДС)
  payment_subject_type INTEGER DEFAULT 4,  -- LIBFPTR_PS_SERVICE (Услуга)
  payment_method_type INTEGER DEFAULT 4,   -- LIBFPTR_PM_FULL_PAYMENT (Полный расчет)
  fiscal_document_number INTEGER,          -- Номер ФД (тег 1040)
  fiscal_sign TEXT,                        -- ФПД (фискальный признак документа, тег 1077)
  fiscal_drive_number TEXT,                -- Номер ФН (тег 1041)
  shift_number INTEGER,                    -- Номер смены (тег 1038)
  receipt_number INTEGER,                  -- Номер чека за смену (тег 1042)
  kkt_reg_number TEXT,                     -- Регистрационный номер ККТ (РН ККТ)
  status TEXT NOT NULL DEFAULT 'pending',  -- 'pending', 'processing', 'fiscalized', 'paper_error', 'failed', 'cancelled'
  is_fiscalized INTEGER DEFAULT 0,         -- 1 = успешно записан в ФН
  is_printed INTEGER DEFAULT 0,            -- 1 = физически распечатан на ленте
  error_code INTEGER DEFAULT 0,
  error_message TEXT,
  device_model TEXT DEFAULT 'АТОЛ 91Ф',
  port TEXT DEFAULT 'COM3',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  fiscalized_at DATETIME
);

CREATE INDEX IF NOT EXISTS idx_fiscal_receipts_tx ON fiscal_receipts(transaction_id);
CREATE INDEX IF NOT EXISTS idx_fiscal_receipts_status ON fiscal_receipts(status);
```

### 3.2. Таблица детального аудита операций `fiscal_audit_logs` (Serilog Sink)
```sql
CREATE TABLE IF NOT EXISTS fiscal_audit_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  timestamp DATETIME DEFAULT CURRENT_TIMESTAMP,
  level TEXT NOT NULL,                     -- 'Debug', 'Information', 'Warning', 'Error', 'Fatal'

CREATE INDEX IF NOT EXISTS idx_fiscal_audit_time ON fiscal_audit_logs(timestamp);
CREATE INDEX IF NOT EXISTS idx_fiscal_audit_event ON fiscal_audit_logs(event_type);
```

## 4. Спецификация серверного C# .NET сервиса (`OrthoErp.FiscalService`)

### 4.1. Конфигурация Serilog с записью в SQLite
В `Program.cs` настраивается Serilog с обогащением контекста и прямой записью в SQLite:

```csharp
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Debug()
    .Enrich.FromLogContext()
    .Enrich.WithProperty("Application", "OrthoErp.FiscalService")
    .WriteTo.Console(outputTemplate: "[{Timestamp:HH:mm:ss} {Level:u3}] [{EventType}] {Message:lj}{NewLine}{Exception}")
    .WriteTo.File("logs/atol-fiscal-.log", rollingInterval: RollingInterval.Day)
    .WriteTo.SQLite(
        sqliteDbPath: config.GetConnectionString("SqliteDb"),
        tableName: "fiscal_audit_logs",
        batchSize: 1)
    .CreateLogger();
```

### 4.2. Потокобезопасная очередь `Channel<FiscalTask>`
- Запросы на печать помещаются в неблокирующий `Channel<FiscalTask>.CreateUnbounded<FiscalTask>(new UnboundedChannelOptions { SingleReader = true })`.
- Клиентский HTTP-запрос ожидает выполнения своей задачи через `TaskCompletionSource<FiscalExecutionResult>` с настраиваемым таймаутом (по умолчанию 35 секунд с учетом медленной механики АТОЛ 91Ф).

### 4.3. Алгоритм устойчивой фискализации (`AtolRecoveryHandler`)
1. **Предварительный сброс (Reset & Warm-up)**:
   - Проверяется текущий подрежим. Если остался незавершенный открытый документ:
     - `fptr.checkDocumentClosed()`: если закрыт $\to$ фиксируем успех;
     - если не закрыт $\to$ вызываем `fptr.cancelReceipt()`.
2. **Открытие документа**:
   - `LIBFPTR_PARAM_REPORT_TYPE = LIBFPTR_RT_SELL` (приход).
3. **Регистрация позиций (Медицинские услуги по ст. 149 НК РФ)**:
   - `LIBFPTR_PARAM_POSITION_PAYMENT_SUBJECT_TYPE = LIBFPTR_PS_SERVICE` (услуга);
   - `LIBFPTR_PARAM_POSITION_PAYMENT_METHOD_TYPE = LIBFPTR_PM_FULL_PAYMENT` (полный расчет);
   - `LIBFPTR_PARAM_TAX_TYPE = LIBFPTR_TAX_NO` (без НДС).
4. **Тег 1008**:
   - Если указан телефон/email пациента, передается параметр `LIBFPTR_PARAM_BUYER_ADDRESS`.
5. **Регистрация оплаты**:
   - `LIBFPTR_PARAM_PAYMENT_TYPE`:
     - Наличные: `LIBFPTR_PT_CASH` (0);
     - Безналичные / Карта: `LIBFPTR_PT_ELECTRONICALLY` (1);
     - СБП / QR: `LIBFPTR_PT_OTHER` (14 / электронные).
6. **Закрытие и обработка сбоев**:
   - Вызов `fptr.closeReceipt()`.
   - Если произошла ошибка или таймаут:
     - **Немедленно вызвать `fptr.checkDocumentClosed()`**.
     - Если `LIBFPTR_PARAM_DOCUMENT_CLOSED == true`:
       - Документ **фискализирован в ФН**!
       - Читаем `LIBFPTR_PARAM_DOCUMENT_NUMBER` (ФД) и `LIBFPTR_PARAM_FISCAL_SIGN` (ФПД).
       - Если `LIBFPTR_PARAM_DOCUMENT_PRINTED == false` $\to$ возвращаем статус `PrintedWithPaperError` с сохранением номера ФД.
     - Если `LIBFPTR_PARAM_DOCUMENT_CLOSED == false`:
       - Вызываем `fptr.cancelReceipt()`, очищаем порт и возвращаем ошибку.

## 5. Интеграция в интерфейс («Оформление визита пациента»)

### 5.1. Шаг 4 мастера (`CheckoutWizard.tsx`):
В блоке выбора способа оплаты добавляется специализированная карточка:
1. **Переключатель**:
   - `[✓] Пробить фискальный чек на ККТ АТОЛ 91Ф` (свитч включен по умолчанию для наличных и карт).
2. **Индикатор состояния кассы**:
   - Зеленый чип: `🟢 АТОЛ 91Ф (COM3) • Касса готова • Смена открыта`
   - Желтый чип: `🟡 Эмулятор ККТ (Тестовый контур без железной кассы)`
   - Красный чип: `🔴 Касса недоступна (Будет сохранена только учетная запись)`
3. **Электронный чек (Тег 1008 ФФД)**:
   - Поле ввода телефона или e-mail пациента с автозаполнением из карточки пациента.
4. **Юридическое примечание**:
   - `Ставка НДС: Без НДС (пп. 2 п. 2 ст. 149 НК РФ — медицинские услуги)`.

### 5.2. Обработчик «Завершить транзакцию и оплатить»:
- При нажатии отправляется единый запрос на сохранение визита:
  - Создаются записи в `operation_transactions`, `transaction_staff_roles`, `procedure_records`;
  - Если активна фискализация, вызывается фискальный контур;
  - В ответ возвращаются `transactionId`, `fiscalDocumentNumber`, `fiscalSign`, `shiftNumber`, `fiscalStatus`.
- На финальном экране успеха:
  - Отображается блок фискализации:
    - **ФД №**: 1042
    - **ФПД**: 3892019482
    - **Смена №**: 14
    - Статус: `🟢 Фискализирован в ФН и передан в ОФД`.
  - При аппаратной ошибке бумаги (`PrintedWithPaperError`):
    - Отображается предупреждение: `⚠️ Чек фискализирован в ФН (ФД #1042), но закончилась чековая лента. Заправьте рулон и нажмите «Повторить печать чека»`.

   - Реализация модуля `server/fiscalRoutes.js` (с очередью фискализации, эмулятором, поддержкой внешнего C# демона, записью в аудит-лог).
   - Создание каркаса C# .NET 8/9 решения `server/fiscal_service/OrthoErp.FiscalService` с Serilog SQLite sink и драйвером ДТО 10.
3. **Этап 3: Доработка интерфейса мастера CheckoutWizard**

   - Поддержка тега 1008 (телефон/email), выбор типа оплаты.
   - Отображение фискальных реквизитов (ФД, ФПД, смена) на экране успеха.
4. **Этап 4: Верификация, сквозное тестирование и документация**
   - Проверка сценариев: успешный чек по карте/наличным, работа с тегом 1008, симуляция сбоя печати, запись логов Serilog в SQLite.
